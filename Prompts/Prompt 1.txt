## 1. Project Overview

A single Node.js bot deployed across **two Discord servers**:
- **Main** (`GUILD_ID_MAIN`) — the public community server. Members, ticket channels, career applications happen here, flight announcements post here.
- **Staff** (`GUILD_ID_STAFF`) — private. Staff identity and permissions live here. Career review, flight briefings, and quota/transcript logs post here.

**Critical architecture rule: staff permission checks are cross-guild.** A user's ability to claim a ticket, review a career application, etc. is determined by their **roles in the Staff guild**, not the Main guild — even though the ticket channel itself lives in Main. Implement a shared helper:

```js
async function isStaffAuthorized(client, discordUserId, requiredRoleIds) {
  const staffGuild = await client.guilds.fetch(process.env.GUILD_ID_STAFF);
  const member = await staffGuild.members.fetch(discordUserId).catch(() => null);
  if (!member) return false;
  return requiredRoleIds.some(id => member.roles.cache.has(id));
}
```
Use this everywhere a "staff-only" action happens, regardless of which guild the interaction fired in.

Five feature systems, built in this order (each depends on shared infra from the last):
1. Core infra (config, Firestore client, timer poller, cross-guild helper, logger)
2. Tickets v2
3. Careers
4. Flight Operations (+ booking webhook stub)
5. VietJet Rewards (loyalty)
6. Paid Ads

## 2. Tech Stack & Non-Negotiable Rules

### Implementation quality requirements
- Inspect the current project before modifying it. Preserve working code where possible and avoid destructive rewrites without cause.
- Use a clear module structure: config, Firebase/Firestore, permissions, timers, logging, commands, interactions, and each feature system should be separated.
- Validate and sanitize all command inputs, webhook payloads, URLs, and user-provided text. Prevent mention abuse by disabling unintended mentions in user-generated messages.
- Verify Discord API and discord.js v14 support for every Components V2 builder and flag used. If the installed version does not support a required API, install/pin a compatible version rather than silently falling back to classic embeds.
- Add structured error handling and actionable logs. Never log bot tokens, Firebase private keys, webhook secrets, or other credentials.
- Include Firestore indexes/rules guidance where needed, a complete `.env.example`, and clear setup, deployment, backup, and troubleshooting instructions.
- Make operations idempotent where retries or restarts are possible. Handle Discord API rate limits, missing members/channels, deleted messages, and unavailable DMs gracefully.
- Include tests for permission gates, timer recovery, and core lifecycle flows where practical. Do not claim a feature is tested unless it was actually run.


- **Node.js + discord.js v14.16+** (need the `ContainerBuilder`/`SectionBuilder`/`TextDisplayBuilder` classes for Components V2 — do not use `EmbedBuilder` anywhere in this bot).
- **Firebase Admin SDK + Firestore** for all persistence.
- **All messages use Components V2** (`flags: MessageFlags.IsComponentsV2`). No classic embeds anywhere in this bot. JSON templates for every message are in this doc — treat them as the source of truth for structure, and build them with the discord.js V2 builders.
- **Every timed action is Firestore-backed, never a bare `setTimeout`/`setInterval` alone.** Write a `timers` collection: `{ type, dueAt, guildId, payload, fired: false }`. Run a poller every `TIMER_POLL_INTERVAL_SECONDS` (default 30s) that queries `fired == false AND dueAt <= now`, executes, marks fired. This must also run once on bot startup to catch anything missed during downtime. This applies to: career question expiry (10 min), ticket join-link deletion (10 min), any flight check-in scheduling.
- **No hardcoded Discord IDs anywhere in source.** Everything in Section 4 comes from `.env`, loaded through a single `config.js` that validates all required vars exist on boot and crashes loudly (not silently) if any are missing.
- **No AI-detection feature.** The careers "AI usage is prohibited" line is reviewer-facing policy text only. Do not attempt to build any AI-content detection into the bot.
- **Role assignment is idempotent.** Check `member.roles.cache.has(id)` before adding; never throw if the role's already present.
- **Local hosting, not cloud.** No assumptions about ephemeral filesystems, no need for Cloud Functions — this runs as a long-lived `node index.js` process on the owner's PC.
- Use **PM2** for process management (`pm2 start index.js --name vietjet-ptfs-bot`) so it auto-restarts on crash. Include a `pm2 save` + `pm2-startup`/`pm2-windows-startup` step in the setup instructions (owner is on Windows based on context — include the Windows path as primary, note the Linux/macOS equivalent in a comment).
- Use `discord-html-transcripts` (npm) for ticket transcript generation — upload the resulting HTML directly as a file attachment to `TICKETS_LOG_CHANNEL_ID`, per the owner's reference implementation ("Tickets V2"). No external storage bucket needed.

### Ticket creation flow
On select: create channel under `TICKETS_CATEGORY_ID`, named per type (`generalsupport-{username}`, `partner-{username}`, `fastpass-{username}`, `report-{username}`, `other-{username}`). Permission overwrites, applied in this order:
1. Deny `ViewChannel` for `@everyone`.
2. Allow `ViewChannel`+`SendMessages` for the opener (member-specific overwrite).
3. Allow `ViewChannel`+`SendMessages` for all roles that can has access to the catergory

**Discord permission caveat — read before implementing step 4.** Role-level overwrites are combined across all of a member's roles by OR-ing the deny bits together and the allow bits together, then subtracting deny and adding allow, *in that order*. That means if a member holds both a blocked role and an allowed role (BoD, Management) on the same channel, the allow can reinstate the bit the deny just removed — the block does not reliably win. A member-specific overwrite (the opener's own) is applied last and beats every role overwrite regardless. Practical effect: `ROLE_IDS_TICKET_BLOCKED` only reliably blocks someone who doesn't *also* hold a role with an explicit allow on that channel. Put this caveat in the README — don't let the owner assume it's an absolute block if they hand that role to someone who's also BoD/Management.

Ephemeral reply to the user using the Opening Message:

```json
{ "flags": 32768, "content": "✅ Your ticket has been created at {ticketChannelLink}." }
```

## 7. Feature Spec: Flight Operations

### Commands
Gated by `ROLE_ID_FLIGHT_OPS_COMMANDS` (Main guild) — a role dedicated to flight commands, separate from the ticket/careers `isStaffAuthorized` check. `ROLE_ID_BOARD_OF_DIRECTORS`/`ROLE_ID_MANAGEMENT_TEAM` (checked in Staff guild) also pass as an admin override by default — `[OPENCODE DECISION]`: drop that override in `isFlightOpsAuthorized` if the owner wants this role to be the *only* way in, no exceptions.

```js
async function isFlightOpsAuthorized(client, discordUserId) {
  const mainGuild = await client.guilds.fetch(process.env.GUILD_ID_MAIN);
  const member = await mainGuild.members.fetch(discordUserId).catch(() => null);
  if (member?.roles.cache.has(process.env.ROLE_ID_FLIGHT_OPS_COMMANDS)) return true;
  return isStaffAuthorized(client, discordUserId, [
    process.env.ROLE_ID_BOARD_OF_DIRECTORS,
    process.env.ROLE_ID_MANAGEMENT_TEAM,
  ]);
}
```

| Command | Effect |
|---|---|
| `/createflight` | Requires `isFlightOpsAuthorized`. Inputs: flight number, scheduled Unix time, aircraft, departure, arrival, private server link, classes, PTFS spawn location, gate number, flight duration, host (defaults to command invoker, overridable). |
| `/logflight flightnum:` | Requires `isFlightOpsAuthorized` OR the invoker is the flight's stored `hostId`. Marks flight completed, logs to Staff guild, cleans up. |
| `/flightupdate flightnum: ...` | Same gate as `/logflight` — role holder, admin override, or the flight's host. Delay (new time) or cancel. |

### `/createflight` flow
1. Validate flight doesn't already exist for that number.
2. **Create a real Discord Scheduled Event** in `GUILD_ID_MAIN` using the input fields (per owner confirmation — auto-create, not link-input). Event description built from:
```
✈️ **{flightNumber}**

🛫 | **Departure:**
🛬 | **Arrival:**
📍 | **Operating Aircraft:**

ℹ️ | **Classes:** Premium, Economy (Business class depending on aircraft)
🕒 | **Flight Time:**

🙂 | **Thank you for choosing VietJet as your airline for this flight!**
```
