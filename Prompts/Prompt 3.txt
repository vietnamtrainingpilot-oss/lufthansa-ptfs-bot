## 4. Member sign-in and sign-out

The user specifically wants members to sign in, sign out, and track their loyalty miles/points on the website. Implement this as a real feature, not just a visual mock-up.

### Authentication approach

1. Inspect the current authentication and backend architecture first.
2. Prefer Discord OAuth2 if compatible with the existing project, because the community's member identity is tied to Discord. Use the official OAuth authorization-code flow with server-side token exchange and secure session handling. Do not expose the client secret or bot token in browser code.
3. Link the authenticated Discord account to the existing canonical member record in Firestore. Use the Discord user ID as a stable identity key where the existing data model supports it. Do not create duplicate accounts for the same Discord user.
4. If the project already has a secure authentication provider, preserve and use it rather than adding a competing login system. Explain the chosen approach.
5. Provide clear Sign in and Sign out actions. After sign-in, show the member's account menu/profile entry and dashboard. After sign-out, clear the session safely and return the interface to the public state.
6. Add and document required environment variables and OAuth callback URLs in the existing environment example and setup guide. Never put real secrets in source control.
7. Validate OAuth state and callback parameters, use secure HttpOnly cookies where session cookies are appropriate, set SameSite and Secure appropriately for the deployment, expire/revoke sessions correctly, and protect state-changing requests against CSRF. Apply rate limiting to authentication endpoints where appropriate.
8. Do not request or store a Discord password. Do not request unnecessary profile permissions. Ask only for the minimum OAuth scopes required, normally identity (`identify`) and only request email if a demonstrated feature requires it.
9. If OAuth cannot be completed because external credentials or callback configuration are unavailable, implement the safe server-side structure and clear setup documentation, but do not claim login works until it has been tested end-to-end. Do not invent credentials or bypass authentication for convenience.

### Authentication states to design and test

- Public visitor: sees public pages and a Sign in action.
- Signing in: clear loading/progress state and understandable error handling.
- Signed-in member: sees account identity and dashboard access.
- Expired or invalid session: gracefully prompts the member to sign in again.
- Signed-out member: cannot access private balances, history, or redemptions.
- OAuth cancelled or failed: returns safely with a helpful message and no broken page.
- Account with no flight history: sees a useful empty state, not fake activity.

## 5. Member dashboard: miles, credits, flights, and rewards

Build a genuinely useful member dashboard, integrated with the existing loyalty/economy implementation.

### Overview panel

Show only values retrieved from the authenticated member's actual server-side record:
- Loyalty balance, using the exact existing data model. The interface may call the loyalty currency “Miles” if this fits the implemented programme, but make the display label configurable and do not create a second, competing points balance.
- Current loyalty tier and progress toward the next tier, calculated from the actual tier rules.
- Separate VJ Credits balance. Never merge credits with loyalty miles/points.
- Number of completed flights and, if the backend reliably tracks it, total distance flown.
- Active missions or challenges and their real progress.
- Available rewards and clear redemption requirements.

Use a clear hierarchy: primary loyalty balance first, tier progress second, then credits and activity. Keep the page usable on mobile and avoid overwhelming the member with too many cards.

### Activity and transaction history

Provide a readable history view with dates, event types, amounts, and statuses for:
- Loyalty miles/points earned from completed flights.
- VJ Credits earned or spent.
- Reward redemptions.
- Reversals, refunds, corrections, and authorized staff adjustments, where visible to the member.
- Mission rewards, if supported by the backend.

Use server-backed pagination or bounded queries. Add filters only if they work. Show clear empty, loading, and error states. Do not expose staff notes, internal audit details, other members' data, private flight links, or sensitive identifiers.

### Flights and rewards

- Show the signed-in member's actual completed flight history, with route, flight number, date, cabin/class, and rewards earned when those fields exist.
- Show upcoming bookings only if the existing booking system stores them reliably.
- Display reward catalogue items and the required currency/cost, eligibility, stock/availability, and redemption conditions.
- Allow redemption only when the backend already supports it or can be safely completed as part of this task.
- Confirm redemptions clearly and show a receipt/result. Handle double-clicks, retries, insufficient balances, unavailable stock, and concurrent requests safely.
- Do not allow the browser to set a balance, choose a trusted price, grant itself miles/credits, alter tier status, or claim a flight was completed.

### Member profile

Provide a small profile/settings area showing the linked Discord identity and basic account information available through the approved OAuth scope. Let the member sign out. Do not create editable profile fields that are not persisted, and do not offer account unlinking unless it can be safely implemented without orphaning or duplicating reward balances.

## 6. Backend, API, and Firestore integrity

- Reuse the existing authenticated API and Firestore collections where possible. Inspect the current schema before proposing new collections.
- The backend must derive the target member from the verified session, not from a client-supplied Discord user ID.
- Every private read must enforce authentication and member-level authorization.
- Every balance-changing mutation must be validated server-side and recorded in an auditable, idempotent transaction ledger.
- Use Firestore transactions or equivalent atomic operations for redemptions and balance updates. Prevent duplicate flight rewards, replayed requests, double redemptions, negative balances, and race conditions.
- Never trust a client-submitted flight status, reward amount, currency amount, tier, eligibility, redemption price, or ownership claim.
- Keep loyalty miles/points and VJ Credits as separate currencies with separate ledgers and clear transaction types.
- Apply pagination and limits to history endpoints; validate inputs; use safe error messages that do not leak secrets or stack traces.
- Configure Firestore security rules so browser clients cannot directly grant or modify balances. Prefer server-mediated access for private financial-like records.
- Do not expose Firebase Admin credentials, OAuth secrets, Discord bot tokens, private server links, staff-only data, or internal API secrets to the client.
- Avoid logging OAuth tokens, session cookies, secrets, or unnecessary personal information.

If the backend currently lacks a safe way to authenticate a member, do not fake a live dashboard. Implement the public rewards page and the documented authentication structure, then clearly report what remains blocked by external setup.
